협업이 계획대로 운영되지 않은 과정

프론트엔드 구현이 이미 완료되어 있고, 백엔드 기능정의서와 일자별 진행 방식까지 부트캠프가 제공한 상태에서 시작된 과제로, 위탁 개발과 유사한 구조였음. 6인 팀으로 시작했으나 개인 사정으로 2인이 초반에 이탈함. 남은 인원으로 역할을 나누자는 제안을 했으나, 팀은 각자 처음부터 끝까지 구현한 뒤 코드리뷰로 가장 완성도 높은 결과물을 선택해 병합하는 방식을 택함. 실제로는 소통 부재로 협업이 이뤄지지 않았고, 같은 API를 여러 명이 중복으로 구현하는 비효율이 반복됨. 결국 교육 마감일에 모여 가장 완성도 높은 구현을 선택하고 병합하는 방식으로 마무리됨. 결과물에 대한 별도의 발표·평가 절차가 없어, 명확한 기준 없이 마무리된 측면이 있었음.

개인 기여

협업 공백 속에서 만든 진행

AI 코드 생성 도구를 적극적으로 활용해 구현했으며, 아래 기여는 코드를 전부 수작업으로 작성한 것이 아니라 문제 진단·방향 설정·AI 결과물의 검증과 조정을 본인이 주도한 것임.

Domain knowledge

실사용 병원 프로그램 기준을 결과물로 제시

팀원 대부분이 병원 백오피스 프로그램(EMR/PACS 등) 사용 경험이 없는 상황에서, 실제 검사 프로그램의 사용 방식을 기준으로 어떤 화면과 데이터 흐름이 필요한지 제시함. 프론트엔드 템플릿을 백엔드 API에 직접 연결해, 환자 등록부터 X-Ray 업로드·AI 예측 결과 표시까지 실제로 동작하는 화면으로 방향을 구체화함.

Integration

프론트-백엔드 계약 불일치 발견 및 수정

이미 구현되어 있던 프론트엔드를 백엔드 API에 실제로 연결하며, 값을 하나씩 입력·클릭해보는 과정에서 계약 불일치 4건(부서·성별 enum 값 불일치, 권한 값 대소문자 불일치, 마이그레이션 미적용으로 인한 500 에러, 응답 스키마 필드 누락)을 직접 발견하고 수정함.

Documentation

팀 회고 문서 작성

프로젝트 종료 시점에 진행 과정 전체와 협업 과정에서 발생한 문제를 총정리한 회고 문서를 작성함.

회고

남은 것과 아쉬운 것

역할 분담을 먼저 제안했으나 팀의 합의를 이끌어내지 못함. 제안이 받아들여지지 않았을 때 대안을 관철시키기 위한 근거 제시와 설득 과정이 더 필요했다는 점을 확인함.

— 역할 분담 제안이 받아들여지지 않은 경험

결과물에 대한 발표·평가 절차가 없을 경우, 협업의 동기와 마무리의 완성도가 함께 약해질 수 있다는 것을 확인함.

— 발표·평가 없이 마무리된 과정

본인 의견을 더 적극적으로 반영해 팀을 설득했다면 더 나은 결과물이 나왔을 수 있다는 아쉬움이 남는 프로젝트였음.

— 프로젝트를 마친 뒤의 소감
AI 도구 활용의 한계 인식 — AI 도구를 적극적으로 활용해 기능을 구현하는 과정에서, 코드를 100% 이해하지 못한 상태로도 기능이 동작하는 경우를 확인함. 이는 이후 학습에서 구현 원리를 직접 검증하는 절차가 필요하다는 것을 시사함.

협업 체계가 계획대로 운영되지 않은 프로젝트였으나, 도메인 지식에 기반한 방향 제시와 프론트-백엔드 통합 검증을 통해 프로젝트를 완성으로 이끄는 데 기여함.
